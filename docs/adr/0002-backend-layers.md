# 0002. Слои бэкенда и доменная модель

Бэкенд разделяется на отдельные проекты `BookingCalendar.Api`,
`BookingCalendar.Application` и `BookingCalendar.Domain`, чтобы зависимости
контролировались компилятором. Application зависит от Domain, API вызывает
Application; Domain не зависит от HTTP, ASP.NET и транспортных DTO.

Domain содержит сущности с поведением, объекты-значения и агрегаты,
защищающие бизнес-инварианты. Application организует пользовательские сценарии.
В API остаются эндпоинты, запуск приложения, регистрация зависимостей,
HTTP DTO, разбор запросов и преобразование результатов в HTTP-ответы.
CQRS и MediatR не используются: сценарии реализуются обычными сервисами.

Рефакторинг сохраняет HTTP-контракт, бизнес-правила и хранение в памяти.
Атомарность бронирования по ADR-0001 и существующие HTTP-проверки сохраняются.

Корень агрегата `Calendar` владеет встречами и создаёт их через операцию
бронирования, защищая отсутствие пересечений между встречами всех типов.
`Meeting` хранит снимок названия и длительности выбранного типа встречи.
`MeetingType` — отдельный агрегат со своими ограничениями.

Содержательные ограничения значений проверяет Domain через фабрики и
объекты-значения. API проверяет структуру JSON и формат даты; Application
передаёт ошибки для преобразования в существующий HTTP-формат.

Application читает время через `TimeProvider` внутри атомарной границы и
передаёт `now` в доменную операцию явно. При бронировании время читается один раз.

Отдельный Infrastructure и репозитории не вводятся: для текущего хранения
в памяти они не дают необходимого разделения ответственности. Состояние
в памяти и синхронизация размещаются в Application; бизнес-инварианты
остаются в Domain.

Модуль регистрации зависимостей находится в Application. API подключает
его вызовом метода расширения, не перечисляя реализации и их времена жизни.
Domain остаётся независимым от DI.

Application предоставляет интерфейсы `IMeetingTypeService`, `IBookingService`,
`IAvailabilityService` и `IMeetingService`. Их реализации отвечают соответственно
за типы встреч, бронирование, слоты и предстоящие встречи. Внутренний
`CalendarState` объединяет состояние в памяти и единую блокировку, но не
содержит бизнес-правил. Все сервисы работают с одним экземпляром состояния.

Публичный статический `Module` в Application предоставляет метод расширения
`AddBookingCalendarApplication`. Он регистрирует интерфейсы и реализации
сервисов, общее singleton-состояние и стандартный `TimeProvider`, сохраняя
возможность подмены времени в тестах. Параметр конфигурации вводится только
при появлении настроек.

Код организуется по папкам с соответствующими пространствами имён:
эндпоинты API находятся в `Endpoints`, транспортные модели — в `Contracts`;
интерфейсы Application — в `Abstractions`, реализации — в `Services`,
состояние — в `State`; доменные агрегаты, сущности, объекты-значения и правила
размещаются соответственно в `Aggregates`, `Entities`, `ValueObjects` и `Rules`.
