# 0001. Атомарность бронирования

- Статус: принято
- Дата: 2026-10-29
- Контекст решения: «Атомарность бронирования: механизм и доказательство»,
  issue #18 карты решений.

## Контекст

Данные сервиса лежат в памяти одного процесса: типы встреч и встречи. Внешней
базы данных нет, второй экземпляр приложения не предусмотрен.

Бронирование обязано быть атомарным: проверка пересечения с существующими
встречами и сохранение новой встречи должны выглядеть для клиента как одна
операция. Если два гостя одновременно отправляют запрос на один и тот же слот,
ровно один получает `201`, остальные — `409 slot-taken`. Частично сохранённых
встреч и `500` из-за гонки быть не должно.

## Решение

Все обращения к in-memory-хранилищу выполняются под единственным `lock` на
объекте хранилища: чтение слотов, чтение встреч, создание встречи и создание типа
встречи. Внутри критической секции — только работа с памятью, без `await` и без
ввода-вывода. Коллекции не читаются и не изменяются вне блокировки.

При создании встречи под блокировкой:

1. один раз читается текущее время;
2. заново проверяются правила слота: сетка стартов, окно записи, рабочие часы и
   `start > now`;
3. проверяется пересечение с существующими встречами по полуинтервалам
   `[start, end)`;
4. встреча вставляется в хранилище.

Снаружи блокировки остаются только разбор запроса и формирование ответа.
Победитель гонки получает `201`, проигравший — `409 slot-taken`.

## Отвергнутые альтернативы

- **`ConcurrentDictionary` по стартам.** Не ловит пересечение: встреча на 60
  минут занимает два старта сетки, а проверять нужно интервал целиком.
- **`SemaphoreSlim(1, 1)`.** Нужен только при `await` внутри критической секции;
  здесь его нет, поэтому `lock` проще и не требует асинхронного API.
- **Неизменяемый снимок и `Volatile`/CAS.** Даёт lock-free чтения, но требует
  второго представления данных и при одном владельце и окне в 14 дней ничего не
  выигрывает.

## Последствия

- Гарантия атомарности действует **в пределах одного процесса**. Данные не
  разделяются между экземплярами, поэтому два экземпляра не конфликтуют, но и не
  видят встреч друг друга.
- Появление второго экземпляра приложения или внешней базы данных означает
  пересмотр механизма целиком, а не точечную замену `lock`.
- Доказательство — HTTP-тест с параллельными запросами: 10 одновременных
  `POST /api/meetings` на один слот, ровно один `201`, остальные
  `409 slot-taken`, итоговый `GET /api/meetings` показывает ровно одну встречу; тест
  повторяется на разных стартах 20 раундов.
- Спецификация ссылается на это решение в разделе о бронировании.
