# Работа агента в Windows

Для поддерживаемых операций Git и gh на Windows использовать запускатель:

1. Записать массив аргументов в `artifacts/agent-command.json`, например
   `["git", "switch", "-c", "chore/topic"]` или
   `["gh", "pr", "create", "--body-file", "artifacts/pr.md"]`.
2. Проверить JSON и выполнить отдельным вызовом ровно
   `node scripts/agent-command.mjs`.
3. Проверить код выхода, затем готовить следующую команду. У запускателя один
   общий файл аргументов, поэтому его вызовы выполнять последовательно.

Запускатель разрешает перечисленные в `scripts/agent-command.mjs` операции,
передаёт аргументы без shell и отклоняет остальные команды. Файл аргументов
остаётся вне git. При отказе песочницы повторить тот же вызов с запросом запуска
вне песочницы; использовать существующее разрешение на запускатель. Если интерфейс
всё же запрашивает подтверждение, проверить фактическую оболочку и сохранённое
правило: инструкция в репозитории сама не предоставляет системных разрешений.

Для правок исходников с кириллицей использовать `apply_patch`. Скрипты сохранять
в файл UTF-8; Windows PowerShell 5.1 может потерять кириллицу при передаче текста
скрипта через stdin в Node. При чтении текста указывать `-Encoding utf8`.

Перед проверками выполнить отдельными вызовами `Get-Command mise` и
`mise exec -- node --version`.
Использовать инструменты проекта через mise, чтобы версии совпадали с CI.

Если каталог mise из WinGet присутствует в PATH, но команда доступна только вне
песочницы, причина — доступ к каталогу установки. Перезапуск Orca сам по себе
не исправляет права песочницы. Для конкретных команд можно настроить постоянные
правила Codex в пользовательском каталоге `~/.codex/rules/`.

## Сохранённые разрешения Codex

При повторных запросах разрешения запустить `mise run agent:permissions`.
Команда проверяет все пользовательские `.rules` штатным `codex execpolicy check`
для Windows PowerShell и встроенного pwsh. Диагностика требует установленный CLI
в `%LOCALAPPDATA%/Programs/OpenAI/Codex/bin/codex.exe` и не входит в Ubuntu CI.
Отсутствие совпадения (`unmatched`) отличается от явного `prompt` и ошибки доступа
песочницы: это разные причины запроса разрешения.

`mise run agent:rules` готовит `artifacts/agent-workflow.rules` для просмотра.
Генератор разрешает перечисленные задачи mise и проверяемые запускатели.
Для PowerShell совпадает весь аргумент `-Command`: перенаправление, дополнительная
команда или произвольный скрипт не разрешаются этим правилом. Рабочие команды
добавляются в список генератора вместе с проверкой policy engine; широкое
разрешение на PowerShell или `node` не требуется.

После проверки сохранить резервную копию пользовательского
`~/.codex/rules/agent-workflow.rules` и установить подготовленный файл на его место.
Запись вне workspace требует системного разрешения. `default.rules` сохраняется.
Повторить `mise run agent:permissions`, затем полностью перезапустить Codex
или приложение, которое запускает его, и открыть новую сессию:
правила читаются при старте. Зелёная диагностика доказывает совпадение правил;
она не доказывает, что уже открытая сессия перечитала их или что песочница даёт
доступ к нужному файлу/сети. В новой сессии проверить реальные рабочие команды.

Если PATH изменён после запуска приложения, полностью перезапустить приложение и затем
создать новую сессию агента. Проверить результат командой `Get-Command mise`.

Команды с постоянным разрешением запускать отдельным вызовом, точно в разрешённой
форме. Подготовку файлов и чтение логов выполнять отдельными вызовами: добавление
других команд или перенаправления меняет строку, сопоставляемую с правилом.
Вывод проверок читать через сессию инструмента запуска — она сохраняет код выхода.

Если нужен файл лога, сохранять его в игнорируемую папку `artifacts/` и обязательно
передавать исходный код выхода. Составной вызов может потребовать отдельного
разрешения:

```powershell
New-Item -ItemType Directory -Force artifacts | Out-Null
mise run test *> artifacts/backend-tests.log
$testExit = $LASTEXITCODE
Get-Content artifacts/backend-tests.log -Tail 60 -Encoding utf8
if ($testExit -ne 0) { throw "Tests failed: artifacts/backend-tests.log" }
```

Сначала прочитать первую ошибку из лога, затем выбирать профильный тест для
повторного запуска. Ошибка доступа к Windows Event Log при старте TestApp —
повод запросить запуск вне песочницы, а не менять код приложения.

Локальная работа Git, чтение и создание issues и PR разрешены пользователем
без повторного согласования. Это не отменяет ограничений песочницы: постоянные
разрешения на команды настраиваются отдельно от инструкций агента.

Восстановление backend с lock-файлами выполнять существующей командой
`mise run install:dotnet`, production-публикацию — `mise run publish:api`.
Для них настраивать отдельные точечные разрешения; произвольный `mise exec`
для этих операций не нужен.

Для публикации рабочей ветки использовать `node scripts/agent-push.mjs`.
Команда отклоняет main/master, detached HEAD и любые аргументы. Git-хук
pre-push по-прежнему запускает `mise run check`. Прямой push в main/master,
перезапись истории и удаление несохранённых данных требуют разрешения.

После изменения локальных разрешений проверить их из новой сессии: чтение issue,
создание рабочей ветки, коммит, публикация ветки и создание PR через запускатели,
а также обе команды восстановления и публикации. Использовать реальные операции
текущей задачи. Критерий успеха — команды завершаются без повторного подтверждения.
Тесты скриптов проверяют их поведение, но не применение разрешений интерфейсом.
Сценарии проверки разрешений и пути двух оболочек заданы в
`scripts/agent-policy-cases.mjs`: его используют тест сгенерированных правил
и диагностика установленных правил. Новые сценарии добавлять в этот общий список.

## Очистка завершённых worktree

Для временных агентных worktree использовать выделенный каталог
`artifacts/agent-worktrees/` корневого checkout и имена `agent-<имя>`:
строчные латинские буквы, цифры и одиночные дефисы между частями имени.
Очистка выполняется из корневого checkout после остановки агентов и процессов,
пишущих в выбранные worktree. На время проверки и удаления каталогами должен
владеть только этот процесс; защита от конкурентной подмены путей не предусмотрена.

1. Записать в `artifacts/agent-worktree-cleanup.json` явное основание интеграции
   и выбранные имена, например:

   ```json
   { "base": "main", "names": ["agent-contract", "agent-review"] }
   ```

2. Проверить список и выполнить отдельной командой
   `node scripts/agent-worktree-cleanup.mjs` без аргументов.
3. Проверить результат для каждого имени и код выхода. При сбое исправить
   указанную причину и повторить ту же команду: отсутствующие каталоги допустимы.

Перед первым удалением проверяется весь список: абсолютные пути, регистрация
в текущем репозитории, чистота и включение HEAD каждого worktree в указанный
`base` по истории Git. Для squash merge сначала самостоятельно перенести нужную
работу: совпадение содержимого не заменяет проверку предка. Symlink и junction
в пути или содержимом worktree отклоняются. Грязные, locked и чужие worktree
сохраняются. Флаги индекса `assume-unchanged` и `skip-worktree` также блокируют
очистку: они могут скрывать изменения от `git status`. Ошибка проверки пути
останавливает удаление.

Каталоги и выбранные prunable-метаданные удаляет только `git worktree remove`.
Параметр `-c core.longpaths=true` действует только в вызовах Git этой команды
и включает поддержку длинных путей Windows при проверке и удалении. Ветки
остаются; глобальный `worktree prune` не вызывается,
поэтому отсутствующие посторонние worktree сохраняют регистрацию. Игнорируемые
артефакты сборки удаляются вместе с выбранным worktree. Если частичное удаление
оставило каталог с изменёнными tracked-файлами, команда остановится как на грязном
worktree: сначала восстановить нужные данные вручную.

Генератор `agent:rules` содержит точное разрешение на эту команду; обновление
пользовательских правил выполняется по процедуре выше. Широкого разрешения
на удаление каталогов или произвольный shell команда не требует.

CLI-регрессии входят в `mise run test:scripts` и Ubuntu CI; отдельный job
`windows-worktrees` запускает их на Windows без сборки продукта. Живая проверка
2026-11-08 на Windows, Node 24.22.1: десять CLI-сценариев прошли, включая junction,
путь длиннее 260 символов, исчезнувший каталог и повторный запуск. Все цели
создавались внутри временных fixtures; пользовательские worktree не удалялись.
Эта проверка подтверждает поведение CLI, а не установку нового разрешения
в пользовательский слой Codex.

## Передача задачи субагенту

Координатор передаёт пути к локальным копиям issue/spec, интеграционную ветку,
базовый commit, границы задачи и канонические команды mise и Git из этого
документа. Указывает зависимости и критерии готовности. Повторно читать GitHub
нужно при изменении задачи или нехватке контекста.
Перед отчётом о готовности выполнить применимые проверки из `mise.toml`;
изменение запускаемых скриптов требует также `mise run agent:ready` (существующие
форматирование и Knip). При ошибке применимой проверки исправить её до передачи
изменения как готового. В отчёте указать базовый и итоговый commit, состояние
рабочего дерева, выполненные команды с результатами и непроведённые проверки.
`agent:ready` не заменяет поведенческие тесты и остальные проверки по области
изменения. Полный check выполняется перед публикацией через pre-push;
повторять его без изменения кода или нового сбоя не требуется.

При ожидающем разрешении сообщить координатору точную команду и состояние
«ожидает разрешения». При проверке существующего разрешения использовать ту же
форму команды, а не создавать новые варианты `mise exec`.

## Интеграция результата исполнителя

Простой fast-forward выполняет координатор. Поддерживаемые Git-команды ниже
на Windows передавать через `artifacts/agent-command.json` и отдельный вызов
`node scripts/agent-command.mjs`, как описано в начале документа. `merge-base`
и `merge` не входят в allowlist запускателя: выполнять их отдельными прямыми
командами Git с разрешением среды, если оно требуется.

1. Зафиксировать ожидаемые интеграционную ветку, её tip, базовый commit
   исполнителя и точный итоговый SHA из отчёта готовности. Проверить отчёт:
   применимые проверки успешны именно для этого SHA, рабочее дерево исполнителя
   чистое, границы задачи соблюдены.
2. В интеграционном checkout проверить `git symbolic-ref --short HEAD`,
   `git status --porcelain=v1 --untracked-files=all` и `git rev-parse HEAD`:
   ветка и tip совпадают с ожидаемыми, вывод status пуст. Проверить
   `git rev-parse <ветка-исполнителя>`: он равен итоговому SHA отчёта.
3. Проверить предков командами `git merge-base --is-ancestor <base> <tip>`
   и `git merge-base --is-ancestor <tip> <SHA>`; обе завершаются с кодом 0.
   Передача относится к записанному base; новый tip интеграции требует повторной
   оценки совместимости и актуальности проверок. При несовпадении ветки,
   грязном дереве или устаревшем отчёте остановиться и устранить причину.
4. Выполнить `git merge --ff-only <SHA>` без конкурентных писателей в checkout.
   Проверить код выхода, равенство `git rev-parse HEAD` итоговому SHA и чистоту
   дерева. Только после этого отметить задачу интегрированной и обновить фронтир.
   Если fast-forward невозможен, сохранить обе истории и передать отдельному
   merger-у базу, оба tip и причину отказа. Reset, force и автоматическое
   переписывание истории для обхода отказа запрещены.
5. После содержательного объединения или исправлений ревью повторить применимые
   проверки для окончательного commit. Полный `mise run check` перед публикацией
   обеспечивает pre-push в checkout публикуемой ветки; дополнительный полный
   запуск обосновать новыми изменениями, сбоем или нерешённым риском. Проверить
   окончательный SHA, чистоту дерева и результат pre-push. PR самостоятельно
   не сливать.

Свидетельства проверки процесса и их ограничения сохранены в
[PR #75](https://github.com/MeNn13/ai-for-developers-project-386/pull/75).
