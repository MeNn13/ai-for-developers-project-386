# Работа агента в Windows

Перед проверками выполнить отдельными вызовами `Get-Command mise` и
`mise exec -- node --version`.
Использовать инструменты проекта через mise, чтобы версии совпадали с CI.

Если каталог mise из WinGet присутствует в PATH, но команда доступна только вне
песочницы, причина — доступ к каталогу установки. Перезапуск Orca сам по себе
не исправляет права песочницы. Для конкретных команд можно настроить постоянные
правила Codex в пользовательском каталоге `~/.codex/rules/`.

Если PATH изменён после запуска Orca, полностью перезапустить Orca и затем
создать новую сессию агента. Проверить результат командой `Get-Command mise`.

Для правок исходников с кириллицей использовать `apply_patch`. Скрипты сохранять
в файл UTF-8; Windows PowerShell 5.1 может потерять кириллицу при передаче текста
скрипта через stdin в Node. При чтении текста указывать `-Encoding utf8`.

Команды с постоянным разрешением запускать отдельным вызовом, точно в разрешённой
форме. Подготовку файлов и чтение логов выполнять отдельными вызовами: добавление
других команд или перенаправления меняет строку, сопоставляемую с правилом.
Вывод проверок читать через сессию инструмента запуска — она сохраняет код выхода.

Если нужен файл лога, сохранять его в игнорируемую папку `artifacts/` и обязательно
передавать исходный код выхода. Составной вызов может потребовать отдельного
разрешения:

```powershell
New-Item -ItemType Directory -Force artifacts | Out-Null
mise run test *> artifacts/backend-tests.log
$testExit = $LASTEXITCODE
Get-Content artifacts/backend-tests.log -Tail 60 -Encoding utf8
if ($testExit -ne 0) { throw "Tests failed: artifacts/backend-tests.log" }
```

Сначала прочитать первую ошибку из лога, затем выбирать профильный тест для
повторного запуска. Ошибка доступа к Windows Event Log при старте TestApp —
повод запросить запуск вне песочницы, а не менять код приложения.

Локальная работа Git, чтение и создание issues и PR разрешены пользователем
без повторного согласования. Это не отменяет ограничений песочницы: постоянные
разрешения на команды настраиваются отдельно от инструкций агента.

Для поддерживаемых операций Git и gh на Windows использовать запускатель:

1. Записать массив аргументов в `artifacts/agent-command.json`, например
   `["git", "switch", "-c", "chore/topic"]` или
   `["gh", "pr", "create", "--body-file", "artifacts/pr.md"]`.
2. Проверить JSON и выполнить отдельным вызовом ровно
   `node scripts/agent-command.mjs`.
3. Проверить код выхода, затем готовить следующую команду. У запускателя один
   общий файл аргументов, поэтому его вызовы выполнять последовательно.

Запускатель разрешает перечисленные в `scripts/agent-command.mjs` операции,
передаёт аргументы без shell и отклоняет остальные команды. Файл аргументов
остаётся вне git. При отказе песочницы повторить тот же вызов с запросом запуска
вне песочницы; использовать существующее разрешение на запускатель. Если интерфейс
всё же запрашивает подтверждение, проверить фактическую оболочку и сохранённое
правило: инструкция в репозитории сама не предоставляет системных разрешений.

Восстановление backend с lock-файлами выполнять существующей командой
`mise run install:dotnet`, production-публикацию — `mise run publish:api`.
Для них настраивать отдельные точечные разрешения; произвольный `mise exec`
для этих операций не нужен.

Для публикации рабочей ветки использовать `node scripts/agent-push.mjs`.
Команда отклоняет main/master, detached HEAD и любые аргументы. Git-хук
pre-push по-прежнему запускает `mise run check`. Прямой push в main/master,
перезапись истории и удаление несохранённых данных требуют разрешения.

После изменения локальных разрешений проверить их из новой сессии: чтение issue,
создание рабочей ветки, коммит, публикация ветки и создание PR через запускатели,
а также обе команды восстановления и публикации. Использовать реальные операции
текущей задачи. Критерий успеха — команды завершаются без повторного подтверждения.
Тесты скриптов проверяют их поведение, но не применение разрешений интерфейсом.
