# Календарь звонков

[![hexlet-check](https://github.com/MeNn13/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/MeNn13/ai-for-developers-project-386/actions)

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: <https://ru.hexlet.io/programs/ai-for-developers>
Как это должно работать: <https://files.hexlet.app/a/2ipc5m>

## Пользовательский сценарий

Владелец календаря один и задан заранее. Гости бронируют встречи без регистрации. Авторизации, личных кабинетов и интеграций с внешними календарями нет.

### Параметры записи

- Часовой пояс — `Europe/Moscow` (UTC+3), единый для владельца и гостей.
- Рабочие часы — понедельник–пятница, 10:00–18:00.
- Окно записи — 14 календарных дней: сегодняшний и следующие 13. Каждый день окно сдвигается на день вперёд.
- Длительность слота равна длительности выбранного типа встречи.
- Шаг доступных стартов — 30 минут. Последний старт выбирается так, чтобы встреча закончилась не позже 18:00.
- Слоты с началом в прошлом недоступны.

### Владелец

1. Открывает страницу владельца — вход не требуется, владелец задан заранее.
2. Создаёт тип встречи: название, описание, длительность.
3. Видит список предстоящих встреч всех типов по возрастанию начала: тип, дата и время, длительность, имя гостя.

### Гость

1. Открывает страницу бронирования без регистрации и выбирает тип встречи.
2. Видит свободные слоты на 14 дней вперёд.
3. Выбирает слот, указывает имя и подтверждает запись.
4. Видит подтверждение на экране, слот исчезает из списка доступных.

### Правила

- Занятый интервал нельзя забронировать повторно — ни целиком, ни частично, в том числе другим типом встречи.
- Встречи могут идти подряд: следующий слот доступен в момент окончания предыдущей.
- Проверка пересечения и сохранение записи выполняются атомарно. Если два запроса на один слот приходят одновременно, успевает только один, второй получает отказ «слот занят».
- Новая запись сразу появляется в списке предстоящих встреч владельца.

## Ограничения

- Данные хранятся в памяти процесса. После перезапуска сервера созданные типы встреч и записи сбрасываются — типы нужно создать заново.
- Письма и уведомления не отправляются.
- Авторизации нет, страница владельца не защищена паролем.

## Стек

- Backend: .NET 10 (LTS), ASP.NET Core Minimal API.
- Frontend: React 19, TypeScript, Vite 8, Mantine 9.
- Контракт: TypeSpec 1.17 → OpenAPI 3.0 → TypeScript-клиент (Orval).
- Тесты: xUnit + `WebApplicationFactory`.
- Линтеры: анализаторы .NET + `dotnet format`, Oxlint, Prettier, rumdl.
- Проверки: jactionlint, agnix, knip, syncpack, vacuum, oasdiff, betterleaks, OSV-Scanner, lychee.
- Окружение: mise, hk, pitchfork.

Версии инструментов зафиксированы в `mise.toml` и `mise.lock`, зависимости — в lock-файлах npm и NuGet.

## Установка

Нужен [mise](https://mise.jdx.dev/). На Windows:

```powershell
winget install jdx.mise
```

На macOS и Linux:

```bash
curl -fsSL https://mise.run | sh
```

Затем:

```bash
git clone https://github.com/MeNn13/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
mise run install
mise run hooks:install
```

`mise install` ставит .NET, Node, pitchfork, hk и вспомогательные линтеры. `mise run install` восстанавливает зависимости .NET и npm.

Для git-хуков `mise` должен быть доступен в `PATH`. В PowerShell включите активацию mise в профиле:

```powershell
mise activate pwsh | Out-String | Invoke-Expression
```

## Использование

Запуск API и фронтенда:

```bash
mise run dev
```

- API: <http://127.0.0.1:5000/api/health>
- Frontend: <http://127.0.0.1:5173>

Управление фоновыми процессами:

```bash
mise daemons status
mise daemons logs api -n 50
mise daemons stop
```

Проверки:

```bash
mise run check
```

Одна команда запускает всё, что можно проверить локально: линтеры (анализаторы
.NET и `dotnet format`, TypeSpec, Oxlint, Prettier, rumdl, jactionlint, agnix,
knip, syncpack, vacuum), поиск секретов, проверку типов, тесты, сборку и сверку
сгенерированных файлов с контрактом. CI вызывает эту же команду.

Ещё в CI есть отдельная задача `audit`:

- `mise run check:audit` — проверки, которым нужна сеть или вся история git:
  уязвимости в lock-файлах (OSV-Scanner), секреты в истории (betterleaks),
  битые ссылки (lychee). Запускается на каждый PR и раз в неделю по расписанию.
- Сообщения коммитов (`commitlint`) и совместимость OpenAPI с базовой веткой
  (`oasdiff`) проверяются прямо в workflow: им нужен диапазон коммитов.

Быстрые проверки изменённых файлов запускаются в `pre-commit`, полный
`mise run check` — в `pre-push`. Автоисправления: `mise run fix`.

Генерация контракта и клиента:

```bash
mise run generate
```

## Docker

Проект собирается в один образ: ASP.NET Core отдаёт и API, и собранный фронтенд
из `wwwroot`, поэтому проверяющему достаточно одного контейнера.

```bash
mise run docker:build
docker run --rm -p 8080:8080 booking-calendar:local
```

- приложение: <http://127.0.0.1:8080>
- проверка: <http://127.0.0.1:8080/api/health>

Полная проверка «образ собирается и контейнер отвечает» — то же, что делает CI:

```bash
mise run docker:check
```

`Dockerfile` линтуется Hadolint в `mise run check`, базовые образы обновляет
Dependabot.

## Структура

