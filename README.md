# Календарь звонков

[![hexlet-check](https://github.com/MeNn13/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/MeNn13/ai-for-developers-project-386/actions)

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: <https://ru.hexlet.io/programs/ai-for-developers>
Как это должно работать: <https://files.hexlet.app/a/2ipc5m>

## Пользовательский сценарий

Владелец календаря один и задан заранее. Гости бронируют встречи без регистрации. Авторизации, личных кабинетов и интеграций с внешними календарями нет.

### Параметры записи

- Часовой пояс — `Europe/Moscow` (UTC+3), единый для владельца и гостей.
- Рабочие часы — понедельник–пятница, 10:00–18:00.
- Окно записи — 14 календарных дней: сегодняшний и следующие 13. Каждый день окно сдвигается на день вперёд.
- Длительность слота равна длительности выбранного типа встречи.
- Шаг доступных стартов — 30 минут. Последний старт выбирается так, чтобы встреча закончилась не позже 18:00.
- Слоты с началом в прошлом недоступны.

### Владелец

1. Открывает страницу владельца — вход не требуется, владелец задан заранее.
2. Создаёт тип встречи: название, описание, длительность.
3. Видит список предстоящих встреч всех типов по возрастанию начала: тип, дата и время, длительность, имя гостя.

### Гость

1. Открывает страницу бронирования без регистрации и выбирает тип встречи.
2. Видит свободные слоты на 14 дней вперёд.
3. Выбирает слот, указывает имя и подтверждает запись.
4. Видит подтверждение на экране, слот исчезает из списка доступных.

### Правила

- Занятый интервал нельзя забронировать повторно — ни целиком, ни частично, в том числе другим типом встречи.
- Встречи могут идти подряд: следующий слот доступен в момент окончания предыдущей.
- Проверка пересечения и сохранение записи выполняются атомарно. Если два запроса на один слот приходят одновременно, успевает только один, второй получает отказ «слот занят».
- Новая запись сразу появляется в списке предстоящих встреч владельца.

## Ограничения

- Данные хранятся в памяти процесса. После перезапуска сервера созданные типы встреч и записи сбрасываются — типы нужно создать заново.
- Письма и уведомления не отправляются.
- Авторизации нет, страница владельца не защищена паролем.

## Стек

- Backend: .NET 10 (LTS), ASP.NET Core Minimal API.
- Frontend: React 19, TypeScript, Vite 8, Mantine 9.
- Контракт: TypeSpec 1.17 → OpenAPI 3.0 → TypeScript-клиент (Orval).
- Тесты: xUnit + `WebApplicationFactory` на бэкенде, Vitest + Testing Library на
  фронтенде.
- Линтеры: анализаторы .NET + `dotnet format`, Oxlint, Prettier, rumdl.
- Проверки: jactionlint, agnix, knip, syncpack, vacuum, oasdiff, betterleaks, OSV-Scanner, lychee.
- Окружение: mise, hk, pitchfork.

Версии инструментов зафиксированы в `mise.toml` и `mise.lock`, зависимости — в lock-файлах npm и NuGet.

## Установка

Нужен [mise](https://mise.jdx.dev/). На Windows:

```powershell
winget install jdx.mise
```

На macOS и Linux:

```bash
curl -fsSL https://mise.run | sh
```

Затем:

```bash
git clone https://github.com/MeNn13/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
mise run install
mise run hooks:install
```

`mise install` ставит .NET, Node, pitchfork, hk и вспомогательные линтеры. `mise run install` восстанавливает зависимости .NET и npm.

Для git-хуков `mise` должен быть доступен в `PATH`. В PowerShell включите активацию mise в профиле:

```powershell
mise activate pwsh | Out-String | Invoke-Expression
```

## Использование

Запуск API и фронтенда:

```bash
mise run dev
```

- API: <http://127.0.0.1:5000/api/health>
- Frontend: <http://127.0.0.1:5173>

Управление фоновыми процессами:

```bash
mise daemons status
mise daemons logs api -n 50
mise daemons stop
```

Проверки:

```bash
mise run check
```

Одна команда запускает всё, что можно проверить локально: линтеры (анализаторы
.NET и `dotnet format`, TypeSpec, Oxlint, Prettier, rumdl, jactionlint, agnix,
knip, syncpack, vacuum), поиск секретов, проверку типов, тесты, сборку и сверку
сгенерированных файлов с контрактом. CI вызывает эту же команду. Правила
тестирования — где unit, где HTTP, где моки — в [AGENTS.md](AGENTS.md#правила).

Ещё в CI есть отдельная задача `audit`:

- `mise run check:audit` — проверки, которым нужна сеть или вся история git:
  уязвимости в lock-файлах (OSV-Scanner), секреты в истории (betterleaks),
  битые ссылки (lychee). Запускается на каждый PR и раз в неделю по расписанию.
- Сообщения коммитов (`commitlint`) и совместимость OpenAPI с базовой веткой
  (`oasdiff`) проверяются прямо в workflow: им нужен диапазон коммитов.

Быстрые проверки изменённых файлов запускаются в `pre-commit`, полный
`mise run check` — в `pre-push`. Автоисправления: `mise run fix`.

Те же задачи доступны через корневой `Makefile`: `make install`, `make dev`,
`make check`, `make lint`, `make test`, `make test-web`, `make build`,
`make generate` и `make fix`. Makefile вызывает задачи mise, поэтому логика
проверок остаётся общей с CI. Нужен GNU Make; на Windows, если `make` не
установлен, используйте команды `mise run` напрямую.

Генерация контракта и клиента:

```bash
mise run generate
```

## Docker

Проект собирается в один образ: ASP.NET Core отдаёт и API, и собранный фронтенд
из `wwwroot`, поэтому проверяющему достаточно одного контейнера.

```bash
mise run docker:build
docker run --rm -p 8080:8080 booking-calendar:local
```

Контейнер запускает приложение автоматически и слушает `0.0.0.0` на порту из
переменной окружения `PORT` (по умолчанию `8080`). Например, другой порт:

```bash
docker run --rm -e PORT=19090 -p 8080:19090 booking-calendar:local
```

- приложение: <http://127.0.0.1:8080>
- проверка: <http://127.0.0.1:8080/api/health>

Полная проверка «образ собирается и контейнер отвечает» — то же, что делает CI:

```bash
mise run docker:check
```

Проверка задаёт `PORT=19090` внутри контейнера и проверяет API, главную страницу
и прямые ссылки `/book` и `/owner`. Это смоук-проверка раздачи страниц;
пользовательские действия в браузере она не выполняет. Внешний порт проверки —
`18080`, его можно изменить переменной `IMAGE_CHECK_PORT`.

Через Makefile: `make docker-build`, `make docker-run`, `make docker-check`.

`Dockerfile` линтуется Hadolint в `mise run check`, базовые образы обновляет
Dependabot.

## Деплой и MCP

Публичного деплоя пока нет: регистрация Railway была недоступна при подготовке
этого шага. Поддержка `PORT` и локальная проверка образа не заменяют проверку
на хостинге. После деплоя сюда нужно добавить публичную ссылку и результат
проверки сценариев гостя и владельца.

Проектная конфигурация Codex находится в `.codex/config.toml`. Railway MCP
отключён (`enabled = false`), пока деплой отложен. Настройка не содержит ключей
или токенов. Порядок подключения владельцем аккаунта:

1. Зарегистрироваться в Railway и убедиться, что аккаунту доступно бесплатное
   размещение Trial/Free без оплаты. Платные тарифы, карта и пополнение для
   этого учебного проекта не используются. При отсутствии бесплатного варианта
   остановиться.
2. В `.codex/config.toml` изменить `enabled` на `true` и перезапустить сессию
   Codex, чтобы загрузить MCP.
3. Выполнить `codex mcp login railway` и пройти OAuth в браузере. Сессию OAuth
   хранит клиент Codex вне репозитория; файлы с токенами и ключами в Git не
   добавлять. Если CLI Codex недоступен, пройти вход через настройки MCP клиента.
4. Перед созданием ресурсов проверить доступный бесплатный кредит и условия
   аккаунта через MCP. Если размещение требует оплаты, ничего не создавать,
   снова установить `enabled = false` и завершить сессию с этим MCP.

Инструкции: [Railway MCP](https://docs.railway.com/ai/mcp-server),
[бесплатные условия Railway](https://docs.railway.com/pricing/free-trial),
[MCP в Codex](https://developers.openai.com/codex/mcp).
Бесплатный кредит ограничен и не гарантирует непрерывную работу сервиса.

Для будущего деплоя нужен один экземпляр приложения, сборка из корневого
`Dockerfile`, порт из `PORT` и проверка `/api/health`. Данные хранятся в памяти
процесса: перезапуск, новый деплой или остановка хостингом сбрасывают типы встреч
и встречи. Несколько экземпляров имеют независимые данные.

При приёмке по публичной ссылке создать тип встречи на странице владельца,
забронировать свободный слот как гость, проверить встречу у владельца и отказ
повторного или частично пересекающегося бронирования через HTTP. Публичную
проверку выполнять в рамках одного запуска приложения.

## Структура

```text
backend/    API, Application, Domain и xUnit-тесты
contract/   TypeSpec, OpenAPI и конфигурация Orval
frontend/   React, Vite, Mantine и сгенерированный клиент
```

Бэкенд разделён на три проекта: `BookingCalendar.Api` содержит `Endpoints`,
транспортные `Contracts` и обработку `Http`; `BookingCalendar.Application` —
интерфейсы `Abstractions`, сценарии `Services`, общее состояние `State` и модуль
регистрации зависимостей; `BookingCalendar.Domain` — `Aggregates`, `Entities`,
`ValueObjects` и чистые `Rules`. Application зависит от Domain, API подключает
Application через `AddBookingCalendarApplication`. Все четыре сервиса scoped
используют единое singleton-состояние с общей блокировкой. Слоты вычисляются
из согласованного снимка типа встречи, времени и занятости.

Данные хранятся в памяти процесса: после перезапуска API типы встреч и записи сбрасываются.

CI описан в `.github/workflows/ci.yml` и запускается на каждый push. Файл `.github/workflows/hexlet-check.yml` не редактируется.
